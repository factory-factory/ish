Create a subcommand in the `ish` terminal app that lists issues in the current project.

Running `ish list` should print a list of all issues in the project. It should behave like standard non-interactive Unix command-line tools with no special colors or formatting.

- **Command-line arguments:** The `ish list` command takes optional query arguments and optional column attributes.

  - `ish list -q '{state != "closed"}'` - filter issues with an expression that removes closed issues from the listing. If multiple `-q` arguments are included, they are implicitly joined with `and` operators.
  - `ish list -c assignees -c state` - include assignees and state in the issue listing. Multiple column arguments may be included.

- **Help screen:** The `ish help` subcommand should describe the useage of `ish list` and show the command line arguments that `ish list` takes.

- **Output format:** The default list format should contain the Issue ID, the date created (in RFC 3339 format), the creator's email address, and the issue title.

## What was done

- Added `ish list` in `list.go`, with `-q/--query` and `-c/--column` flags that can each be repeated. Several `-q` queries are parsed separately and joined with `and`, each one grouped, so an `or` in one query can't leak into another. Queries resolve lookups like `.user.email` and `:user` the same way the TUI's custom filter does (`app.resolveFilter` is now exported as `app.ResolveFilter` so the command can share it).
- `ish help` lists the new command, and `ish help list` / `ish list --help` describe the output format and flags, with examples.
- `store.Summary` now includes the issue's `Author` (email), and the new `store.Attributes` returns the values of the attribute keys you name for every issue.
- Tests are in `list_test.go` and `store/issues_test.go`.

## Choices I made that you may want to change

1. **Output format.** Columns are separated by tabs, one issue per line, sorted by ID, with no header row. Tabs keep the output easy to pipe into `cut`, `awk`, and so on, since titles contain spaces. Example: `3DEVJ-T9438<TAB>2026-10-26T15:10:31-07:00<TAB>brendan@berg.industries<TAB>Create ish list subcommand`.
2. **Where `-c` columns go.** They're added *after* the title, so the four default columns always stay in the same positions. Would you rather have them before the title?
3. **Attributes with several values or none.** Several values are joined with commas and no spaces (e.g. `alice@example.com,bob@example.com`). An issue without the attribute gets an empty column. Emails appear without angle brackets, as the database stores them.
4. **No default filter.** `ish list` with no `-q` prints every issue, closed ones included, as the ticket says. The TUI hides closed issues by default, so tell me if `list` should do the same.
5. **Messages about the database.** `ish list` builds or syncs the metadata database the same way the TUI does, but writes those messages ("Indexed new issue: …") to stderr so stdout contains only the listing. If there's no `.ish/` directory, it exits with an error instead of creating one the way `ish init` does.
6. **Unknown `-c` names.** A `-c` key that no issue uses just prints an empty column, so a typo like `-c asignees` is silently blank. Should it be an error or a warning on stderr? Also, should `-c` accept the built-in fields (`@title`, `@author`, `@dateModified`, …) as well as attributes?
7. **Tabs or newlines in values.** These aren't escaped. Titles are single lines, so this only matters if an attribute value or title contains a tab. Let me know if you want them escaped.

I'm leaving the state as `in progress` until these questions are answered.
