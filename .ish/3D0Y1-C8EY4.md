[Claude <noreply@anthropic.com> 2026-10-24T21:19:15-07:00]

Thanks. I'll use fsnotify v1.10.1.

**On 3:** I'll treat "edited in the TUI since being opened" as the issue having unsaved changes: its `dirty` flag, or a card or tag edit still in progress. Without unsaved changes, the issue just reloads.

**On 5:** you're right, notifications in `.ish/` can't tell a `git pull` from any other edit. Worse, some history changes produce no notifications in `.ish/` at all. For example, `git commit` of an issue you've already edited adds a modification date without touching any issue file.

What does reliably change is git's own state. Each time HEAD moves, git appends a line to `.git/logs/HEAD`: on a commit, pull, merge, rebase, checkout, or reset. So I'd watch that file as well (found with `git rev-parse --git-path logs/HEAD`, so worktrees work), and when it changes, run `IndexHistory` and `IndexUsers`. `IndexHistory` only reads commits newer than the newest one it has, so this is cheap.

Caveats:

- The reflog is on by default in a normal checkout, but can be turned off with `core.logAllRefUpdates=false`. History would then update only at start-up, as it does today.
- Outside a git repository, nothing extra is watched.
- `IndexHistory` only adds commits newer than the newest one it has. So after a pull that brings in commits _older_ than ones already indexed, which is common with merges, those older commits are missed until the next full index. I'd fix that by having `IndexHistory` look for commits it doesn't have yet, rather than only newer ones, which is still cheap.

Should I include this watching of git's state in this ticket, with the fix to `IndexHistory`? Or leave history start-up only for now, and do it as a separate ticket?

[Claude <noreply@anthropic.com> 2026-10-24T21:29:13-07:00]

Done. Git state isn't watched, as agreed.

- **Watching** (new `watch` package, using fsnotify v1.10.1): ish watches `.ish/` while it runs. Changes to `.md` files are reported once, 100 ms after the last of a burst. The metadata database, `config.toml`, editors' swap and backup files, and permission changes are ignored. If watching can't start, ish says so and runs without it.
- **Syncing:** each change runs `store.Sync`. It runs in the UI's update loop, not in the background, so it can never write the database at the same time as one of ish's own saves. ish's own saves don't count as changes, since their checksums already match.
- **List:** it refreshes with the current filter, and the selected issue stays selected.
- **Open issue, no unsaved edits:** it reloads in place, keeping the same tag or card selected and the same scroll position.
- **Open issue with unsaved edits:** a dialog says the file was changed outside ish, and offers **Discard my edits**, which loads the file, or **Keep my edits**, which saves the issue over the file immediately. "Unsaved edits" means changes not yet written, or a field open for editing, even if nothing has been typed in it yet. Other keys are ignored until one is chosen. **Keep my edits** is selected first, since those are what's being worked on. If a field was being edited, it stays open after either choice to keep, and is saved when finished, as before.
- **Open issue deleted:** without edits, ish returns to the list with "… was deleted outside ish". That includes an issue ish was started with, which then shows the list rather than quitting. With unsaved edits, the same dialog asks whether to discard them and close the issue, or keep them and save the file again. You didn't specify this case, but quietly dropping the edits seemed wrong.
- **Unreadable file:** if the open issue's file can't be parsed, for example while half-written or with merge-conflict markers, the last good version stays shown, with the error above the help. It reloads once the file can be read.

Tests: `watch/watch_test.go` covers which events are reported, rename-into-place saves, bursts, and closing. `app/watch_test.go` covers the list, reloading, ish's own saves, both dialog answers for changed and deleted files, editing in progress, single-issue mode, and unreadable files. `models/follow_test.go` covers keeping the selection and scroll position, `Unsaved`, `Save`, and notices. The whole suite passes, and the watcher passes with `-race`. I also checked in a real terminal that outside edits update the list and the open issue, and that both dialog answers do the right thing.
