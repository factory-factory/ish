## Expressions

Expressions are syntactic constructs that transform values. They are used for mathematical operations, string manipulation, date manipulation, and type conversions.

Expressions may appear as an r-value in place of a literal, and must be enclosed in parentheses.

Examples:

- `(3 + 7)`
- `(.user.email :lower)`

## Precedence

Unary operators bind tightest, then function application. Operators follow normal precedence rules.

## Binary operations

The simplest form of expression is a binary operation. The filter expression language supports the standard mathematical operators `+`, `-`, `*`, `/` `%` (remainder), and `**` (exponentiation); and comparison operators `=`, `!=`, `<`, `<=`, `>`, and `>=`.

## Functions

Functions in filter expressions are designed to be chained, so they always take at least one argument and return a value. The first argument is always the value being passed through the chain. Additional arguments may follow the function name if enclosed in parentheses. Functions always start with a colon.

For example, an expression to convert a string to lower case would look something like `('YELLING' :lower)`. A function like `join`, which takes a list to join and a string to join with would be written as `([1, 2, 3] :join(','))`.

Functions are to be implemented as application-defined SQLite functions written in go. The functions to be implemented as part of the initial implementation are:

- **String manipulation:** `:lower`, `:upper`, `:join`, `:split`, `:replace`, `:trim`
- **Collection operations:** `:count`, `:distinct`, `:includes`, `:indexof`
- **Numeric operations:** `:abs`, `:ceil`, `:floor`, `:round`, `:max`/`:min` (`max` and `min` operate on a collection of numbers)

## Plan

### Syntax

```
value      = literal | lookup | "(" expression ")"
expression = comparison
comparison = sum [ ( "=" | "!=" | "<" | "<=" | ">" | ">=" ) sum ]
sum        = product { ( "+" | "-" ) product }
product    = power { ( "*" | "/" | "%" ) power }
power      = chain [ "**" power ]
chain      = unary { function }
unary      = ( "-" | "+" ) unary | operand
function   = ":" name [ "(" expression { "," expression } ")" ]
operand    = literal | lookup | list | "(" expression ")"
list       = "[" [ expression { "," expression } ] "]"
```

- **Precedence:** following the ticket, unary operators bind tightest, then functions, then `**`, then `*` `/` `%`, then `+` `-`, then comparisons. So `(-.x :abs)` is `abs(-x)`, and `(1 + .x :abs)` is `1 + abs(x)`.
- **Associativity:** `**` groups from the right, and the others from the left. A comparison can't be chained, so `(a < b < c)` is an error.
- **Lists:** these are new. I've assumed a JSON-like `[…]` from the `:join` example.

### Evaluating expressions

- **In SQLite:** expressions are compiled into SQL, as the ticket asks. Functions are Go functions registered with SQLite, as `ish_regexp` is now, such as `ish_lower(?)`.
- **Lookups:** these are still resolved from one snapshot, and passed as parameters.
- **Lists:** SQLite has no list type, so lists would be passed between functions as JSON arrays, which SQLite's `json_each` can read.
- **Checks when parsing:** unknown functions, and the wrong number of arguments.
- **Checks when running:** type errors, such as `:lower` on a number, are found when the query runs. They're shown under the filter, like a lookup's type error.

### Display

`String()` prints expressions back as they're written. I'd colour them as follows:
- the parentheses yellow, like other parentheses
- operators bold bright white, like comparison operators
- function names aqua, like lookups

Each is easy to change.

## Syntax

- **Where expressions go:** an expression in parentheses can be used wherever a value can, as in `{estimate > (.base * 2)}` or `{assignees = (.user.email :lower)}`.
- **Operands:** literals, lookups, lists (`[1, 2, 3]`) and parenthesized expressions.
- **Precedence**, from tightest:
  - unary `-` and `!`
  - functions, so `(-.x :abs)` is `abs(-x)`, and `(1 - 2 :abs)` is `1 - abs(2)`
  - `**`, which groups from the right
  - `*`, `/` and `%`
  - `+` and `-`
  - one comparison: `=`, `!=`, `<`, `<=`, `>` or `>=`
- **Chained comparisons:** these are an error, as in `(a < b < c)`.
- **Functions:** these start with a colon and chain. Their arguments are expressions, in parentheses, as in `:join(',')` or `:join(('+' :upper))`.
- **Checked when parsing:** an unknown function, or the wrong number of arguments. For example, `:replace takes 2 arguments`.
- **Regular expressions:** a regular expression literal can still only follow `~` directly. Inside an expression, a string works as a pattern, as in `{state ~ ('^IN ' :lower)}`.
- **Display:** expressions are printed as they're written, with spacing normalized. Parentheses and brackets are yellow, operators are bold bright white, and function names are aqua, like lookups.

## Types and values

- **Operators:** arithmetic needs numbers, and `+` doesn't join strings. `=` and `!=` need two values of the same type, and `<`, `<=`, `>` and `>=` need two numbers or two strings. A mismatch is an error, as is a function given the wrong type.
- **Division:** `/` divides exactly, so `(7 / 2)` is `3.5`. Dividing by zero, or `%` by zero, gives `null`.
- **`null`:** as in SQL, an operator or function given `null` gives `null`, as does a lookup that finds nothing. A comparison with a `null` value is UNKNOWN, as with a missing lookup.
- **Lists:** as on the right of a comparison, a list matches if any of its values does. `!=` matches if none does.
- **Errors:** an expression's error, such as `('a' + 1): + needs two numbers, not a string and a number`, is shown under the filter, and the filter isn't applied.

## Functions

- **Strings:**
  - `:lower` and `:upper`
  - `:join(separator)`, which joins a list's strings, numbers and booleans
  - `:split`, which splits on whitespace, or `:split(separator)`
  - `:replace(old, new)`, which replaces plain text, every occurrence
  - `:trim`, which removes whitespace, or `:trim(characters)`, which removes those characters
- **Lists:**
  - `:count`
  - `:distinct`, which keeps the first of each value, in order
  - `:includes(x)`
  - `:indexof(x)`, which counts from 0, and gives `null` if the value isn't there
- **Numbers:**
  - `:abs`, `:ceil` and `:floor`
  - `:round`, to whole numbers, or `:round(places)`
  - `:max` and `:min` of a list of numbers, which give `null` for an empty list

## How they're evaluated

- **In SQL:**
  - each operator and function is an SQL function written in Go, as the ticket asks
  - `ish_binary` and `ish_unary` handle the operators, and functions are named `ish_` followed by their name, such as `ish_lower`
  - `ish_compare` compares an attribute's value with the expression's value
- **How values pass between them:** as JSON text, so strings, numbers, booleans and lists keep their types, and a mismatch is an error rather than a conversion by SQLite.
- **Lookups:** these are resolved from one snapshot, and passed as parameters.
- **Checking first:** every operand is a literal or a lookup, so an expression's value is the same for every issue in a query. So, when a filter is applied, `filter.Resolve` also evaluates each expression once in Go, with the same code. That catches type errors before the query runs. It also finds a `null` value, which makes the comparison UNKNOWN.
- **Later:** if fields or attributes become operands, the SQL functions are already in place.

## Testing

- **Precedence:** unary operators before functions, `**` from the right, and arithmetic before comparisons.

- **Functions:** each one, including their optional arguments, empty lists, chaining and expressions as arguments.
