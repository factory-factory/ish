When parsing bylines in a markdown file, update the parser so that any text preceding an email address enclosed in angle brackets is treated as a display name and added to the `user` table.

## Proposed syntax:

- Bylines start with `[` and end with `]`.
- A byline consists of an optional display name, an email address, and a timestamp.
- If a display name is presesnt, the email address _must_ be enclosed in angle brackets.
- If no display name is present, the email address _may_ be unenclosed.
- The display name and email combination should follow RFC 5322's mailbox specification in section 3.4.

## In this change:

**SQLite schema:**

- Update the `user` table schema to include a timestamp column.
- Remove the unique index on `name, email`.
- Make the `userName` and `userEmail` indexes unique.

**Initialization behavior:**

- Update the `ish` init behavior so that the commit's date created is listed when getting authors from `git log`.
- Update the markdown parser to extract the display name as well as email from the byline.
- When a byline with a display name is encountered, add the display name <-> email relationship to the directory and to sqlite.
- When inserting records into the `user` table, update the row only if the new entry's date created is newer than the existing entry.

Done, following your answers, and moved to `in review`.

## Bylines

- **The form:** a byline is an RFC 5322 mailbox, then a timestamp, in brackets.
- **The mailbox:** either a bare `addr-spec`, or a display name followed by an `addr-spec` in angle brackets. The name is words, quoted strings, or a mix of the two. Comments and obsolete forms aren't accepted.
- **Examples:**
  - `[alice@example.com …]`
  - `[<alice@example.com> …]`
  - `[Alice Liddell <alice@example.com> …]`
  - `["Liddell, Alice" <alice@example.com> …]`
- **Rejected:** a byline without an email, such as `[Claude …]`, doesn't parse. Neither does a name with a bare email, as in `[Alice alice@example.com …]`.
- **Dots in names:** an unquoted name can't contain a dot, since that's one of RFC 5322's obsolete forms. So `Dr. Alice <…>` needs quoting, as `"Dr. Alice" <…>`.
- **Timestamps:** everything after the mailbox is the timestamp, so timestamps with spaces still parse, such as `2023-05-28 11:55:23 -0400`.
- **Round trips:** the author is kept as it's written, so files are written back unchanged.
- **Where it lives:** the parser is `models.SplitMailbox` and `models.ParseMailbox`, used by the issue parser, the store and the display.

## Bylines ish writes

- **The format:** new issues and comments are signed with git's `user.name` and `user.email`, as `"Brendan Berg" <brendan@berg.industries>`, with the name always quoted.
- **No `user.name`:** the byline is just the email.
- **No `user.email`:** ish falls back to the current user, as before. A byline doesn't accept that, so the issue can't be saved until `user.email` is set, and the save shows an error. Would you like a different fallback?

## Showing bylines

- **With a user:** a byline shows the user's newest name from the `user` table, as `@Name`.
- **Without one:** a byline shows its own display name. With no display name, it shows the email on its own.

## The `user` table

- **The new column:** `dateCreated`, in UTC RFC 3339.
- **The indexes:** `userName` and `userEmail` are unique, and the `(name, email)` index is gone.
- **The schema version:** it's now 4, so databases are rebuilt.

## What adds users

- **The git history:** git authors are listed with their commit's author date (`%aI`). Where a name and email have several commits, their newest date is kept.
- **Bylines:** each byline with a display name adds its user, dated by the byline's timestamp. This happens whenever an issue is indexed: on init, during the start-up sync, and when an issue is saved.

## How users are added

- **A new email:** it's added.
- **A newer name for an email:** it replaces the older name, and the row's date is updated.
- **An older name:** it's skipped.
- **A name another email already has:** it's skipped, however new, and reported as, for example, `Skipped user "Alice" <alice@work.example>: the name is already used by alice@example.com`.
- **Where conflicts are reported:** `ish init` and each start report them to stderr, from the git history and from re-indexed files.
- **A known gap:** a save from the issue view has nowhere to show a notice, so a conflicting byline there is skipped quietly. The next start's sync doesn't re-index that file, since it's already up to date, so it isn't reported then either.
- **Repeated notices:** a conflict in the 50 most recent commits is reported at every start, until it's resolved.

## Testing

- **The mailbox parser:**
  - bare and bracketed emails
  - names of words, quoted strings with escapes, and non-ASCII letters
  - the text after the mailbox, including timestamps with spaces
  - the forms that aren't accepted
  - quoting names and reading them back
- **The byline parser:** each byline form parses and is written back unchanged, and bylines without an email are rejected.
- **Adding users:** a new user, a newer name, an older name, the same name seen later, a name another email has (both newer and older), and a user without a name.
- **Conflict messages:** the text of a conflict notice.
- **Git authors:**
  - parsing the dates, with the newest kept, and in a real repository with set author dates
  - init uses every commit, and the start-up indexing the latest 50, reporting conflicts
- **Byline users:** bylines with names add their users on init and on sync, with conflicts reported, and a byline without a name adds none.
- **The table:** names and emails are each unique.
- **The current author:** a quoted name and email, quotes escaped, no name, and no email.
- **A new issue:** its byline has the name, saves, and adds its user.
- **Updated tests:** test bylines now use emails, since they're required.

  - adding a comment wrote `["Brendan Berg" <brendan@berg.industries> …]`, and bylines showed `@Brendan Berg`
